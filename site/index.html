About

I know many programmers are not good at packaging their repositories. I am the same: I like keeping my head down and building.

Now that vibe coding is everywhere, I have started to think that giving passers-by a reason to look twice might matter.

That is how RepoCover came to be. I made it in a day. It looked pretty good, so I started using it myself.

The evidence decides

A screenshot is evidence. It is not automatically the design.

RepoCover first judges what the repository already gives it. Good material is preserved and recomposed. Distracting UI is removed. Missing structure is rebuilt only as far as the evidence supports.

A

Existing product UI

Keep the recognizable interface, crop around the real interaction, and remove browser chrome, debug clutter, or broken fragments.

B

Brand or hero asset

Preserve the project's own character, dimensionality, palette, and visual role while rebuilding the surrounding composition.

C

No useful image

Infer a truthful visual system from the project's objects, actions, topology, and result—without pretending a previous cover exists.

How it works

Read first. Draw second.

Questions

The short version.

Does it work without a screenshot?

Yes. RepoCover can infer a visual direction from repository evidence, but it will not invent runtime proof or pretend it saw an interface that was never available.

Can it use an existing web app?

Yes. An accessible local preview or working frontend usually produces the strongest result because the real interface can be inspected and selectively recomposed.

Does every cover look alike?

No. The output size and quality checks are consistent; the palette, subject, dimensionality, layout, and materials follow the project.

Will it upload the image to GitHub?

Only when separately requested. Creating the files and changing repository settings are two different authorization boundaries.
